# M1 — Netcode and movement vertical slice: status

**State: code complete and verified without Unity; not yet run in Unity or on an iPhone.**
Everything engine-independent (movement, collision, netcode, touch-control logic, dev server, bots)
is tested in CI and load-tested over real UDP. The Unity side (client views, HUD, camera, dedicated
server host) compiles against the real Unity 6000.3 assemblies but has **not been executed**: that
needs the Unity license secret for CI and your iPhone via TestFlight. The milestone's exit criteria
(real iPhones on a cloud server) are therefore **not met yet** — see "Open items".

**End-to-end scenario tests** (server + clients on the simulated network, 120 fps, virtual time):
prediction matches the server at 0/80/150 ms latency with jitter and up to 10% loss (≤ 3 corrections
in 10 s of wandering with jumps and sprints; settles within 1 cm); a server teleport snaps the
prediction; remote players move smoothly (no backwards steps, ≤ 0.1 m per frame, ≤ 0.4 s behind);
sending inputs 4× faster gives no speed (≤ sprint speed); resume within grace keeps id and
position, and the player is removed after it; clean quit removes at once; protocol mismatch,
full server, disabled dev auth, silent and malformed connections are rejected with reasons;
interest radius and the every-3rd-tick far rate hold; 119 visible players split into packets under
the 504-byte minimum limit (and 2 parts once the MTU grows); backgrounded players stop and don't
starve, also under 80 ms jitter.

**Test totals:** 120 `dotnet test` tests (all pure C#, the same files Unity's Test Runner compiles).

## Load tests (real UDP, `sim/loadtest.sh`)

One machine (4 vCPU cloud container) runs the dev server and all bots. Simulated **30–60 ms delay
in each direction and 2% loss in each direction**; 60 s after ramp-up. Bots stay within ~150 m of
each other, so **every bot sees every other bot** (worst case for bandwidth). Raw results:
[M1-loadtest/](M1-loadtest/).

| Bots | Server tick avg | Tick max (after warm-up) | Server CPU | Server upload | Per bot down (payload / wire) | Per bot up | RTT avg | Corrections (steady state) |
|-----:|----------------:|-------------------------:|-----------:|--------------:|------------------------------:|-----------:|--------:|---------------------------:|
| 30 | 0.13 ms | 2.2 ms | 7% | 2.9 Mbit/s | 10.1 / 11.9 KB/s | 0.8 KB/s | 150 ms | 2 in 29 bot-minutes (max 0.22 m) |
| 50 | 0.21 ms | 1.7 ms | 8% | 7.5 Mbit/s | 16.3 / 18.8 KB/s | 0.8 KB/s | 139 ms | 6 in 49 bot-minutes (max 0.22 m) |
| 100 | 0.85 ms | 7.5 ms | 15% | 29.9 Mbit/s | 31.5 / 35.8 KB/s | 0.8 KB/s | 139 ms | 0 |

The tick budget is 33.3 ms. The first 5 s of the 30/50-bot runs had one 17–18 ms tick (JIT warm-up
while bots joined). No connection was lost; no snapshot exceeded the packet limit.

**Found and fixed by the load test:** at 100 bots the server crashed. Snapshots were split at a fixed
1100 bytes, but LiteNetLib's single-packet limit starts at 504 bytes and grows with MTU discovery,
so it threw once ~75 players were in view. Snapshot parts are now sized per connection; oversize
sends are counted and dropped instead of throwing. The simulated network enforces the 504-byte
worst case, so tests cover it.

**Caveats:** server and bots shared 4 cores, so the server numbers are pessimistic for CPU but not
representative of a real cloud VM's network. Bots are .NET processes, not iPhones; phone-side
numbers (FPS, thermal, battery, real cellular conditions) are still to be measured.

## How the Unity code was checked without Unity

`tools/unity-compile-check` extracts the real Unity 6000.3.27f2 managed assemblies (and the iOS Xcode
extension) from GameCI's public editor images, takes the Input System 1.20.1 source, and builds one
project per asmdef with Unity's defines: **iOS player, Linux server, editor, iOS editor — all
compile with 0 errors and 0 warnings in our code.** It catches wrong Unity APIs and cross-assembly
`internal` access (shown with a deliberate error). It does not run anything: runtime behavior,
rendering, shaders, IL2CPP and the URP editor setup are unverified until `ci-unity` has a license.

## Changes from the plan (recorded)

- **FishNet → LiteNetLib + own netcode** (ADR 0007), at the M1 decision gate.
- **Greybox map is generated in code at runtime** (same layout on server and client) instead of by
  editor tools: no scene/prefab files, and collision can't drift from visuals.
- **`tools/loadtest` became `sim/Kindling.Bots` + `sim/loadtest.sh`.**
- **HUD uses IMGUI** for M1 (no assets needed); the real UI (and HUD editor) comes with the UI work
  in M2/M3.
- **Measurements recorded here and in ADR 0007** instead of a separate ADR.

## Known limitations (planned)

- **IPv6-only networks:** joining by IPv4 literal fails on NAT64-only networks (Apple tests App
  Review on these). Servers must be joined by hostname before App Store submission (M2 server browser
  passes hostnames).
- **Dev auth only:** the game server accepts anyone; join-ticket verification lands with the M2
  Unity work.
- **Float determinism** across ARM64/x64 is close, not bit-exact; reconciliation absorbs it (as
  designed, ADR 0007). To be measured on real devices.
- Snapshots aren't delta-compressed yet (31 KB/s per player with 100 in view is fine for Wi-Fi/LTE;
  delta compression is planned before larger player counts).
